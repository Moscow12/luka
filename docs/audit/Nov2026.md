| | |
|---|---|
| **Audit date** | 18 November 2026 |
| **Branch / commit** | `feature/update-dasher` @ `338749b` |
| **Stack** | Laravel 12.32.0, Livewire 3.6.4, PHP ^8.2, MySQL, Reverb, Spatie Permission 6 / Activitylog 4 |
| **Scope** | All routes (`web`, `api`, `channels`, `console`), 167 Livewire components, 6 HTTP controllers + 2 middleware, models, services, policies, jobs, commands, Blade views, `config/`, `.env`, `public/`, seeders, Composer and npm dependencies, and committed repository content |

---

## 1. Executive summary

The application has some well-built security components (chat, tickets, performance evidence and the sync-API token guard), but the platform as a whole is **not safe to expose to untrusted users or to the internet in its current state.**

The core problem is **systemic broken access control.** Every web route is protected only by the `auth` middleware, and **116 of 167 Livewire components contain no authorization check of any kind.** Any authenticated employee, including the most junior account, can:

- reset any user's password and give themselves any role (full administrative takeover);
- create or edit roles and assign every permission;
- download any file the web server can read (including `.env`) through a path traversal in the backup module, and download or restore full database dumps;
- run operating-system commands on the server through the fingerprint-device module;
- upload a `.php` or `.html` file into the public web root;
- read and modify any employee's salary, contracts, disciplinary records, qualifications and documents, and generate payroll.

Separately, an **unauthenticated** attacker can take over any account by brute-forcing the 6-digit password-reset code, which is not rate limited, and is then trusted for 2FA for 30 days. A **hard-coded super-admin credential** and a **10 MB legacy HR database dump containing PII** are committed to the repository and pushed to GitHub.

2. **Lock down the dangerous modules today**, even before the full RBAC rollout: add `abort_unless(auth()->user()->can(...), 403)` to `mount()` **and to every action** in `UserManagement`, `Acl/*`, `Backuprecovery`, `Fpdevices`, `Smsapis`, `Settings`, payroll and all `Hr/Staffs/*` components (C-01, C-02).
3. **Fix the RCE and file-read sinks:** `basename()` plus an allow-list for backup filenames, array-form `Process::run([...])` for device commands, and `mimes:` allow-lists with private-disk storage for all uploads (C-03, C-04, C-05).

5. **Upgrade dependencies:** `composer update` (Laravel, Livewire, PhpSpreadsheet, CommonMark, Guzzle, Symfony, dompdf) and `npm audit fix` (H-08).

## 2. Risk rating method

**Severity = Impact × Likelihood**, adjusted for exploit preconditions.

- **Impact:** confidentiality, integrity and availability of HR, payroll and medical-adjacent personal data, and of the host server.
- **Likelihood:** *High* means any authenticated user or the internet can exploit it with a browser and DevTools. *Medium* needs specific knowledge, timing or a network position. *Low* needs privileged access or unusual conditions.
- Because Livewire public properties and action arguments are fully controllable by the client (an attacker can edit them through DevTools, `Livewire.find(id).set(...)` / `.call(...)`, or by replaying `/livewire/update` requests), **every public Livewire method is treated as an HTTP endpoint**, and every unlocked public property as user input.

## 3. Critical findings

### C-01 Systemic broken access control: authorization missing from 116 of 167 Livewire components

| | |
|---|---|
| **Severity** | 🔴 Critical (CVSS 3.1 ≈ 9.9, AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H) |
| **Category** | OWASP A01 Broken Access Control / IDOR |
| **Likelihood** | High: any logged-in user |
| **Affected** | `routes/web.php` (all groups use `middleware('auth')` only); 116 components with no `can()`, `authorize()`, `abort_*`, `hasRole()` or Gate call |

**Description.** No route uses `can:`/`permission:` middleware, and most components never check permissions in `mount()` or in their actions. The permissions the app seeds (`manage-users`, `manage-roles`, `manage-permissions`, `manage-backups`, `manage-settings`, `generate-payroll`, `view-payroll`, …) are defined in `database/seeders/PermissionSeeder.php` but **are not enforced server-side**. Only 5 `@can`/`@role` directives exist in all views, so menu hiding is not even consistently applied, and menu hiding would not be a control anyway.

**Most sensitive unprotected components:**

| Area | Components (all under `app/Livewire/`) | What any user can do |
|---|---|---|
| Identity / ACL | `Users/UserManagement.php`, `Acl/RoleCreate.php`, `Acl/RoleShow.php`, `Acl/PermissionIndex.php`, `Acl/RoleIndex.php` | See C-02 |
| System | `Setup/Backuprecovery.php`, `Setup/Settings.php`, `Setup/Smsapis.php`, `Setup/Smslogs.php`, `Setup/Finances.php`, `Setup/Approvalconfigurations.php`, `Setup/Approval/*`, `Setup/Finance/*`, `Setup/Workstation.php`, `Setup/Departments.php`, … | Dump or restore the DB, change approval chains, change SMS gateway, change tax and allowance tables |
| Payroll | `Acc/Payroll/Payrollgeneration.php`, `Allowancepayment.php`, `Paymentreports.php` | Generate payroll, view everyone's pay |
| Employee records (IDOR) | `Hr/Staffs/{Staffdetails,Addstaff,Salary,Contracts,Promotions,Disciplinary,Qualifications,Dependants,Otherdocuments,Digitalsignature,Leave,Attendance,Importstaffs}.php` | Read or modify **any** employee by changing `{id}` in `/hr/staffs/*/{id}`, bulk-import employees |
| Leave / loans | `Hr/Leave/{Requestleave,Leaveapproval,Leavebalance,ActingAssignmentSettings}.php`, `Hr/Loan/*` | See H-05, H-06 |
| Attendance | `Hr/Attendance/{Fpdevices,Managefpusers,Managefpattendance,Checkindata}.php` | Command injection (C-04), forge attendance |
| Contracts | `Contracts/{ManageContracts,ContractForm,ContractDetails}.php`, `Hr/Contract/*` | Create, edit and delete institutional contracts |
| Audit | `Audit/Auditlog.php` | Read the full activity log (all PII changes, role changes) |
| Budget / Chop / Performance setup | `Chop/*`, `Performance/OrganizationalPlans/*`, `Performance/TitleKpis/*` | Alter budgets, plans and KPIs |

**Proof of concept (safe):**
1. Log in as a low-privilege employee.
2. Browse to `/hr/staffs/salary/<any-employee-uuid>`. The page renders full salary data. `saveSalary()` writes to the public, unlocked `$employee_id`.
3. Browse to `/setup/backuprecovery` or `/users/management`. Full functionality is available.

**Impact.** Complete loss of confidentiality and integrity of all HR, payroll and personal data, and a path to full server compromise (C-03, C-04, C-05).

**Remediation.**
1. Add route-level permission middleware as a coarse first gate, for example:
   ```php
   Route::prefix('setup')->middleware(['auth', 'can:manage-settings'])->group(...);
   Route::get('management', UserManagement::class)->middleware('can:manage-users');
   ```
2. **Also** authorize inside every component. Route middleware does not protect subsequent `/livewire/update` calls if a component is embedded elsewhere, and actions need their own per-record checks:
   ```php
   public function mount() { $this->authorize('manage-users'); }
   public function saveUser() { $this->authorize('manage-users'); ... }
   ```
3. For per-employee pages, create `EmployeePolicy` (`view`, `update`, `viewSalary`, `viewDisciplinary`) that allows HR roles, the employee themself, and the employee's line supervisor (reuse `App\Support\DepartmentSupervision`). Call `$this->authorize('view', $employee)` in `mount()` and before each write.
4. Add a CI test that iterates all Livewire routes as a role-less user and asserts 403, except for an explicit allow-list of self-service pages.

**Verification.** As a user with no roles, every non-self-service route returns 403, and direct `Livewire.find(...).call('saveUser')` attempts return 403.

### C-02 Privilege escalation and account takeover via User Management and ACL components

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A01 Broken Access Control / privilege escalation |
| **Likelihood** | High |
| **Affected** | `app/Livewire/Users/UserManagement.php:124-264`, `app/Livewire/Acl/RoleCreate.php:18-38`, `app/Livewire/Acl/RoleShow.php:33-66` |

**Description.** `editUser()`, `saveUser()`, `disableUser()` and `enableUser()` accept any user ID and perform no authorization. `saveUser()` sets a new password (`$userData['password'] = Hash::make($this->password)`) and `syncRoles([$role])` with any role ID. `RoleShow::updateRole()` can attach every permission to any role, and `deleteRole()` deletes roles.

**PoC.**
1. As any user, open `/users/management` and click Edit on your own row (or call `editUser('<admin-uuid>')`).
2. Set *Role* to the administrator role and save. Your account is now admin.
3. Alternatively, edit the administrator's account, set a new password, then log in as them.

**Impact.** Full administrative takeover by any authenticated user, and lock-out of legitimate admins (`disableUser`).

**Remediation.** Authorize with `manage-users` / `manage-roles` in `mount()` and in each action. Prevent users from editing their own roles. Prevent non-super-admins from granting roles they don't hold. Require re-authentication (`password.confirm`) for password resets and role grants. Invalidate the target's sessions after an admin password reset. Apply the strong password rule from `ChangePassword` here too (see M-06).

**Verification.** A user without `manage-users` gets 403 on page load and on direct action calls. A role-grant audit entry is written only for authorized actors.

> **Remediation status (18 Nov 2026): fixed in code, pending deployment.** `UserManagement` requires `manage-users`, `RoleIndex`/`RoleCreate`/`RoleShow` require `manage-roles`, and `PermissionIndex` requires `manage-permissions`. These are enforced at the route **and** in each component's `boot()`, so they run on every Livewire request. `App\Services\Acl\AccessControl` applies a no-escalation rule: a non-super-admin can grant or edit only roles whose permissions they hold, can add only held permissions to a role, can manage only accounts whose access is within their own, and can never manage super-admins. Users cannot change their own role, edit or delete a role they hold, or disable themselves. Every user, role and permission change requires a fresh password confirmation (`ConfirmsAdminPassword`, 15 minutes, rate limited, resumable actions allow-listed and locked). Admin-set passwords use the strong policy (M-06). Disabling an account or resetting its password ends the user's sessions and rotates the remember token (M-03). The M-01 XSS in `permission-index` is fixed. Covered by `tests/Feature/Acl/AdminAuthorizationTest.php` (18 tests).

### C-03 Path traversal in backup download, delete and restore (arbitrary file read, delete and write) plus unauthenticated-by-role DB dump/restore

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A01 / A03 Path traversal, CWE-22; A05 |
| **Likelihood** | High (any user, see C-01) |
| **Affected** | `app/Livewire/Setup/Backuprecovery.php:222-236` (`downloadBackup`), `:238-254` (`deleteBackup`), `:270-316` (`restoreBackup`), `:63-74` (`createBackup` name) |

**Description.** User-supplied filenames are concatenated directly into paths:
```php
$path = storage_path("app/backups/{$filename}");   // downloadBackup / deleteBackup
return response()->download($path);
```
- `downloadBackup('../../../.env')` resolves to `<base>/.env`. **Any user can read `.env` (APP_KEY, DB, mail, Reverb and API secrets)** and any other file readable by PHP.
- `deleteBackup('../../../public/index.php')` gives arbitrary file deletion (DoS, or deleting `.htaccess`).
- `backup_name` such as `../../public/x` causes `createBackup()` to write a ZIP containing the full **database dump** into the public web root, where it can be downloaded unauthenticated.
- `restoreBackup()` executes whatever SQL is in a chosen archive against the production DB (`mysql ... < backup.sql`) and calls `ZipArchive::extractTo()` without entry-name validation (zip-slip).
- Leaking `APP_KEY` also enables forging encrypted cookies, Livewire snapshot checksums and signed URLs, and decrypting every `EncryptedFileStore` attachment.

**PoC (safe, read-only):** As a low-privilege user on `/setup/backuprecovery`, run in the browser console:
`Livewire.find('<component-id>').call('downloadBackup', '../../../.env')`. The browser downloads `.env`.

**Remediation.**
```php
$filename = basename($filename);
abort_unless(preg_match('/^[A-Za-z0-9_\-]+\.zip$/', $filename), 422);
$path = storage_path('app/backups/'.$filename);
abort_unless(str_starts_with(realpath($path) ?: '', realpath(storage_path('app/backups')).DIRECTORY_SEPARATOR), 404);
```
- Apply the same sanitisation to `backup_name` (`alpha_dash`), and generate the name server-side.
- Require `manage-backups` **and** super-admin plus password confirmation for create, download, restore and delete.
- Prefer a vetted package (e.g. `spatie/laravel-backup`) and encrypt backups at rest. Move restore out of the web UI into an artisan command.
- Pass the MySQL password via `MYSQL_PWD` env or `--defaults-extra-file`, not on the command line (it is visible in `ps`).

**Verification.** `downloadBackup('../../../.env')` returns 422/404. Unit test traversal strings (`../`, `..%2f`, absolute paths).

> **Remediation status (18 Nov 2026): fixed in code, pending deployment.** `App\Services\Backup\BackupManager` now owns all naming and path handling: server-generated names, an allow-list regex, `realpath` containment, and symlink refusal. Archives are AES-256 encrypted (`BACKUP_ARCHIVE_PASSWORD`, `0600` files, `0700` directory) and validated entry by entry against zip-slip, symlinks, unexpected roots and size limits. The UI requires `manage-backups` plus a backup-specific password confirmation (15 min, rate limited). Downloads go through a 60-second signed URL bound to the user. Restore is removed from the web UI and is available only as `php artisan backup:restore`, which takes a safety backup first and never calls `extractTo()`. `mysqldump`/`mysql` receive credentials through a `0600` option file. Covered by `tests/Feature/Backups/BackupSecurityTest.php` (36 tests). **To finish:** set `BACKUP_ARCHIVE_PASSWORD` and run `php artisan backup:protect` to encrypt the three legacy archives.

### C-04 OS command injection in fingerprint-device sync (remote code execution)

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A03 Injection, CWE-78 |
| **Likelihood** | High: any user can create a device (C-01) |
| **Affected** | `app/Livewire/Hr/Attendance/Fpdevices.php:542` (also `:272`, `:324`, `:375-390`, `:525`, `:593`) |

**Description.** Device credentials are only validated as `nullable|string|max:255` (`:119-120`) and then interpolated into a shell command inside single quotes:
```php
Process::timeout(200)->run("{$pythonCmd} {$pythonScript} {$device->ip_address} {$daysBack} '{$username}' '{$password}' 2>&1");
```
A password containing `'` breaks out of the quoting. `clearDeviceLogs()` also builds Python source code by interpolation and wraps it in `-c '...'`. `ip_address` (validated `ip`) and `port` (validated `integer`) are currently safe, but only by coincidence of validation.

**PoC (do not run in production).** Create an Anviz device with password `x'; id > /tmp/pwned; echo '`, then trigger *Sync*. The command runs as the PHP user.

**Impact.** Full server compromise: read `.env`, pivot to the DB and the internal network (devices sit on the LAN).

**Remediation.**
- Always use **array form**, which bypasses the shell:
  ```php
  Process::timeout(200)->run([$pythonCmd, $pythonScript, $device->ip_address, (string) $daysBack, $username, $password]);
  ```
- Pass secrets via environment (`->env([...])`) or stdin rather than argv.
- Replace the inline `python -c` script with a fixed script file that receives arguments.
- Note that `base_path('public/...')` contains a space (`APP SU`) and is currently unquoted, which breaks these commands on this host. Array form fixes that too.
- Move the Python scripts out of `public/` (see M-07). Restrict the module to an `manage-fp-devices` permission.

**Verification.** A device password containing `'`, `;`, `$()`, or backticks is passed literally to the script, and no extra process is spawned.

### C-05 Unrestricted file upload to the public web root (RCE / stored XSS)

| | |
|---|---|
| **Severity** | 🔴 Critical (RCE if the web server executes `.php` outside `index.php`; otherwise High via stored XSS) |
| **Category** | A04/A05, CWE-434 |
| **Likelihood** | High |
| **Affected** | `app/Livewire/Hr/Staffs/Disciplinary.php:107-123`, `Qualifications.php:109-127`, `Promotions.php:126-144`, `Otherdocuments.php:99-114` (rule `['file','max:10240']`, no `mimes`) → `->store('attachments', 'public')` |

**Description.** These uploads accept **any file type** and store them on the `public` disk (`storage/app/public`, symlinked to `public/storage`). Laravel's `store()` derives the extension from the detected MIME type, so a file starting with `<?php` is saved as `attachments/<hash>.php`, and an HTML/SVG file as `.html`/`.svg`. On Apache with `mod_php`, or nginx with a generic `location ~ \.php$` block, requesting `/storage/attachments/<hash>.php` executes it. An HTML/SVG upload served from the app origin gives stored XSS and session hijack. The global Livewire temp rule (`config/livewire.php`) only limits size, and `preview_mimes` includes `svg`.

**PoC (safe variant).** Upload an `.html` file containing `<script>alert(document.domain)</script>` as an "other document", then open the stored URL from the record. The script runs on the application origin.

**Remediation.**
- Add strict allow-lists everywhere: `['file','mimes:pdf,jpg,jpeg,png','max:10240']`, plus `mimetypes:` for defence in depth.
- Store HR documents on the **private** `local` disk (or reuse the existing `App\Support\EncryptedFileStore`) and serve them through an authorizing controller, as `TicketAttachmentController` already does.
- Remove `svg` from Livewire `preview_mimes`.
- Web server: deny script execution under `/storage` and `/uploads` (nginx: `location ^~ /storage/ { location ~ \.php$ { deny all; } }`; Apache: `php_flag engine off` / `RemoveHandler .php` in `storage/app/public/.htaccess`).

**Verification.** A `.php`, `.html` or `.svg` upload is rejected with a validation error. Existing files under `storage/app/public/attachments` are scanned for non-document extensions.

> **Remediation status (18 Nov 2026): fixed in code, pending deployment.** All HR document uploads (staff contracts, promotions, qualifications, disciplinary, other documents, leave, contract requests, HR letters, institutional contracts) are validated by `HrDocumentStore::rules()`. A file passes only if its client extension, its content-guessed extension and its detected MIME type all match the allow-list: PDF/JPG/JPEG/PNG for every HR document type. Word files (`.doc`/`.docx`) are not accepted. The content is checked again at store time. Files are stored AES-256 encrypted on the private disk and served only through `HrDocumentController` (`/hr/documents/{type}/{id}`). The path comes from the record, never the request, and access follows `HrDocumentAccess` (the employee, `view-staff`/`manage-staff`, department supervisors, plus leave approvers and contract-request reviewers where relevant). This also closed three validation bypasses found during the fix: leave documents and contract-request attachments were only validated when a client-controlled flag or request type said so, and the staff photo had no validation at all. The staff photo is now restricted to JPEG/PNG and stays public. The Livewire temporary-upload rule now enforces an app-wide type allow-list, and `svg` was removed from `preview_mimes`. **To finish:** run `php artisan hr-documents:secure` (report), then `--apply`. On the audited copy it reported 5 documents to encrypt and 39 unreferenced HR files in `public/storage` to quarantine, with no dangerous file types present.

### C-06 Hard-coded super-admin credentials committed to source control

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A07 Identification & Authentication Failures / A02, CWE-798 |
| **Likelihood** | High: the repository is pushed to a GitHub remote |
| **Affected** | `database/seeders/UserSeeder.php:18-33` |

**Description.** The seeder creates a super-admin (`is_super_admin = true`, which bypasses all Gates via `Gate::before` in `AppServiceProvider`) with a **fixed, guessable password derived from the admin's email address**. Anyone with repository access, or who guesses the pattern, gets full control on any environment where the seeder ran and the password wasn't changed. *(The literal value is intentionally not reproduced in this report.)*

**Remediation.**
- Change this account's password on every environment **immediately**.
- Make the seeder read `env('SEED_ADMIN_PASSWORD')`, or generate a random password, print it once, and force a change on first login.
- Remove `is_super_admin` and `id` from `User::$fillable` (`app/Models/User.php:32-54`) so they can never be mass-assigned.
- Consider the repository history exposed. Rotate as above even after editing the seeder.

**Verification.** `grep -n "Hash::make('" database/seeders` returns nothing. Logging in with the old password fails.

### C-07 Unauthenticated account takeover by brute-forcing the password-reset code (also bypasses 2FA)

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A07, CWE-307 / CWE-640 |
| **Likelihood** | Medium–High (automatable; no account needed) |
| **Affected** | `app/Livewire/Auth/ForgotPassword.php`, `app/Livewire/Auth/ResetPassword.php:52-151`, `app/Models/PasswordResetToken.php` |

**Description.**
- The reset code is 6 digits (10⁶ space) and valid for 15 minutes. `verifyToken()` has **no attempt limit, no throttling and no delay**, and a new code can be requested at will.
- `$email` is a public, unlocked property initialised from `?email=` and is fully client-controlled.
- After a successful reset, the flow **logs the user in and auto-registers the current browser as a trusted device for 30 days** (`:121-143`), so 2FA is skipped from then on.
- `ForgotPassword` confirms whether an email exists (`exists:users,email` with a custom message), which enables targeting.

**PoC outline.** Request a reset for `victim@org`. Script parallel `verifyToken` calls across `000000–999999` against `/livewire/update`. At roughly 100 req/s, ~9% of the space is covered per 15-minute window, and repeating windows succeeds in hours. On a hit, set a new password: the attacker is logged in and trusted.

**Remediation.**
- Throttle per email and per IP, e.g. `RateLimiter::attempt('reset:'.$email, 5, ..., 900)`. Invalidate the code after 5 failed attempts.
- Use a long random token in a signed link (Laravel's built-in `Password` broker), or at least 8+ alphanumeric characters.
- Mark `$email` `#[Locked]`, or keep it server-side in the session.
- **Do not auto-trust the device after a reset.** Require 2FA on the next login. Notify the user by email when their password changes.
- Return a generic "If an account exists, a code was sent" message.
- Store token hashes, not plaintext, and compare with `hash_equals`.

**Verification.** The 6th wrong code within 15 minutes is rejected regardless of correctness, and the token is invalidated. No `TrustedDevice` row is created by the reset flow.

| | |
|---|---|
| **Severity** | 🔴 Critical (personal-data breach) |

| **Likelihood** | High: tracked in git and pushed to `origin` (GitHub) |

## 4. High findings

### H-01 2FA can be redirected to any account (tamperable `$email`) with no attempt limit

| | |
|---|---|
| **Severity** | 🟠 High |
| **Affected** | `app/Livewire/Auth/TwoFactorsAuthentication.php:154-259`; `app/Models/TwoFactorToken.php` |

**Description.** After passing the password step with *any* valid account, the 2FA component trusts its public `$email` property for both `resendCode()` and `verifyTwoFactor()`. An attacker can change `$email` to the victim's, trigger a code to the victim, then brute-force the 6-digit code (10-minute TTL; the only control is `sleep(1)`, which parallel requests ignore). On success, `Auth::login($victim)` is called. The token lookup and `markAsUsed()` are also non-atomic, so concurrent requests can reuse a single code. **2FA is currently disabled** (`TWO_FACTOR_ENABLED=false` in `.env`), so all accounts rely on passwords alone, and login itself is not throttled (H-04).

**Remediation.** Keep the pending user ID in the server session only (`session('2fa_user_id')`) and never in a public property, or use `#[Locked]`. Throttle verification (5 attempts per code) and resends. Consume the token atomically (`UPDATE ... WHERE used = 0`, then check affected rows). Enable 2FA in production, at least for privileged roles.

**Verification.** Changing `email` in the Livewire payload has no effect. The 6th wrong code is rejected.

### H-02 Trusted-device "fingerprint" is trivially spoofable (2FA bypass)

| | |
|---|---|
| **Severity** | 🟠 High (when 2FA is enabled) |
| **Affected** | `app/Services/DeviceFingerprinter.php:15-27`, `app/Livewire/Auth/Login.php:50-82` |

**Description.** The "trusted device" identity is `sha256(User-Agent | first 3 IPv4 octets | Accept-Language | Accept-Encoding)`. All of these are attacker-controlled headers, and the /24 network is shared by everyone behind the organisation's NAT or Wi-Fi. An attacker with a stolen password on the same network, sending a common browser's headers, skips 2FA.

**Remediation.** Issue a random, long-lived, `HttpOnly; Secure; SameSite=Lax` **device cookie** whose hash is stored in `trusted_devices`, bound to the user. Validate the cookie, not headers. Allow users to view and revoke trusted devices, and revoke all on password change.

### H-03 Unauthenticated attendance injection endpoint

| | |
|---|---|
| **Severity** | 🟠 High (integrity of attendance, roster and potentially payroll) |
| **Affected** | `routes/api.php:18`, `app/Http/Controllers/Api/AttendanceLogController.php` |

**Description.** `POST /api/attendance/receive` sits outside the `api.token` group and has no authentication, no rate limit and no validation beyond presence. Anyone who can reach the server can insert unlimited clock-in records for any `fpuser_id` (fake presence, or fill the DB).

**PoC.** `curl -X POST https://host/api/attendance/receive -H 'Content-Type: application/json' -d '[{"user_id":12,"timestamp":"2026-11-18 07:00:00"}]'` returns `"inserted":1`.

**Remediation.** Move the route into the `api.token` group (or a per-device HMAC/IP allow-list). Add `throttle:60,1`. Validate `user_id` (exists in `fpusers`) and `timestamp` (`date`, within an acceptable window). Cap array size.

### H-04 No rate limiting on authentication endpoints; user enumeration

| | |
|---|---|
| **Severity** | 🟠 High |
| **Affected** | `app/Livewire/Auth/Login.php:29-45`, `ForgotPassword.php:20-26`, `TwoFactorsAuthentication.php`, `ResetPassword.php`; `bootstrap/app.php` (no `throttle` on `api` group) |

**Description.** No `RateLimiter`/`throttle` is used anywhere except chat (`ChatService.php:233`). Passwords can be brute-forced or credential-stuffed (login accepts email, username **or** phone number). Forgot-password can be used to mail-bomb users and confirms whether an address exists.

**Remediation.** In `Login::loginUser()`:
```php
$key = 'login:'.Str::lower($this->login).'|'.request()->ip();
if (RateLimiter::tooManyAttempts($key, 5)) { throw ValidationException::withMessages(['login' => __('auth.throttle', ['seconds' => RateLimiter::availableIn($key)])]); }
RateLimiter::hit($key, 60); // on failure; RateLimiter::clear($key) on success
```
Apply the same to forgot, reset and 2FA flows. Add `throttle:api` to the API group. Use generic responses. Log failed logins (re-enable `LoginActivity`, see L-07).

### H-05 Client-tamperable Livewire state used for authorization-relevant fields (mass assignment)

| | |
|---|---|
| **Severity** | 🟠 High |

| **Affected** | `Hr/Leave/Requestleave.php:79,85,65` (`$employee_id`, `$status`, `$end_date`) → `Employeeleaves::create([... ### H-06 Segregation-of-duties and business-logic flaws in approvals

| | |
|---|---|
| **Severity** | 🟠 High |
| **Affected** | `app/Livewire/Hr/Loan/Loanapproval.php:164-323`; `app/Livewire/Hr/Leave/Leaveapproval.php:169-232`; `Requestleave.php:454-460` |

**Description.**
- **Loans:** any user linked to an employee record can approve, reject or mark under review **any** loan, **including their own**. The only check is `hasEmployeeAccount`.
- **Leave:** `Leaveapproval` correctly checks the approver's level and department, but does not prevent approving one's own request if the approver is mapped to their own level. **Remediation.** Gate loan approval with a `approve-loans` permission plus approval-level mapping. Block `loan.employee_id === approver.employee_id` and `leave.employee_id === approver.employee_id`. Wrap decisions in `DB::transaction()` with `lockForUpdate()` on the request row and re-check its status inside. Validate `days` against the remaining balance server-side.

## 5. Medium findings

### M-01 Stored XSS via Alpine/Livewire expression injection in `wire:click`

**Affected:** `resources/views/livewire/procurement/orders.blade.php:320`, `chop/department-budget-request.blade.php:367`, `chop/activities-management.blade.php:328`, `acl/permission-index.blade.php:90,127`.
**Description.** User-controlled names are placed inside JavaScript string literals in `wire:click="addItem('{{ $item->name }}', ...)"`. Blade's HTML-escaping (`'` → `&#039;`) is decoded by the browser before Alpine evaluates the expression, so a product, category or permission name such as `x'); alert(document.cookie); ('` executes script for every user who views the list. Creating such records is open to any user (C-01).
**Remediation.** Pass only IDs and look up names server-side: `wire:click="addItem(@js($item->id))"`. Where strings are necessary, use `@js($value)` / `Js::from()`, never `'{{ }}'`.
**Verification.** An item named `a');alert(1);('` renders inertly.

### M-02 Missing HTTP security headers and CSP

**Affected:** no middleware sets them (`bootstrap/app.php`, `app/Http/Middleware/`).
**Description.** There is no `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors` (clickjacking of approval buttons), `Strict-Transport-Security`, `Referrer-Policy`, `Permissions-Policy` or `X-Content-Type-Options` on HTML responses. File controllers set `nosniff`, which is a positive.
**Remediation.** Add a `SecurityHeaders` middleware to the `web` group. Start with CSP in report-only mode (`default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`, plus the Reverb `connect-src`), then enforce. Set HSTS at the TLS terminator.

### M-03 Session and cookie hardening gaps

**Affected:** `config/session.php`, `.env`, `UserManagement::disableUser()`, `ChangePassword`.
**Description.** `secure` is unset, so cookies are sent over HTTP. Session payloads are stored unencrypted in the DB. Disabling a user (soft delete) or an admin password reset **does not terminate the user's existing sessions or remember-me tokens**. `ChangePassword` does not call `Auth::logoutOtherDevices()`. The 30-day "remember device" also sets a Laravel remember-me cookie.
**Remediation.** Set `SESSION_SECURE_COOKIE=true` and `SESSION_ENCRYPT=true`. On disable or password reset, delete the user's rows from `sessions`, rotate `remember_token`, and deactivate trusted devices. Call `logoutOtherDevices()` on password change. Consider a shorter idle timeout for HR/payroll roles.

### M-04 Sync API: single all-powerful static token, token logged, full PII returned

**Affected:** `app/Http/Middleware/VerifyApiToken.php`, `app/Http/Controllers/Api/*.php`, `routes/api.php`.
**Description.**
- One shared token grants create, update and read on employees, leaves, contracts and assets. There are no scopes, no per-client identity, no rotation story and no IP allow-list.
- The token may be sent as a **body field**, and `LeaveController.php:59`, `AssetController.php:60`, `AttendanceController.php:22,86` log `$request->all()`, which **writes the secret (and PII) into log files**.
- `EmployeeController::index/show` serialise the whole `Employee` model (no `$hidden`), including national ID and TIN.
- `$e->getMessage()` is returned in JSON errors (`EmployeeController.php:547,578`, `ContractController.php:229,332,354`, `LeaveController.php:201`, `AttendanceController.php:71,140`).
- There is no throttling.
- Sync payloads can set file paths (`photo`, `signature`) and `added_by`.

**Remediation.** Prefer Sanctum personal access tokens with abilities (per partner). Accept the token only in the `Authorization` header. Redact with `Arr::except($request->all(), ['token'])` before logging. Return API Resources with explicit fields. Return generic errors. Add `throttle:api` and an IP allow-list.

### M-05 Error and exception detail disclosure to end users

**Affected:** `Setup/Backuprecovery.php:123,314`, `Hr/Attendance/Fpdevices.php` (multiple `getMessage()` flashes), `Hr/Staffs/Importstaffs.php:182`, `Hr/Attendance/Managefpusers.php:103`, API controllers (M-04).
**Description.** Raw exception messages (SQL fragments, file paths, shell output) are flashed to the UI. Combined with `APP_DEBUG=true` (H-09), internals are widely exposed. The global `QueryException` renderer in `bootstrap/app.php` is a good pattern; extend it.
**Remediation.** Log `report($e)` and show a generic message with a correlation ID.

### M-06 Inconsistent password policy

**Affected:** `Users/UserManagement.php:177-179` (`min:8`), `Auth/ResetPassword.php:30,80` (`min:8`) vs `Users/ChangePassword.php:26-31` (strong rule with mixed case, numbers, symbols, `different`).
**Remediation.** Define `Password::defaults(fn () => Password::min(12)->mixedCase()->numbers()->symbols()->uncompromised())` in `AppServiceProvider` and use `Password::defaults()` everywhere.

### M-07 Web-root hygiene: scripts, archives and bytecode served publicly

**Affected:** `public/anviz_*.py`, `public/zkteco*.py`, `public/__pycache__/`, `public/build.zip` (tracked), `public/tanzania_full_geodata.json`.
**Description.** Internal device-integration scripts (protocol details, default credential handling) and a build archive are downloadable by anyone. The Python scripts are executed by the app from `public/` (C-04), so tampering with them would also be dangerous.
**Remediation.** Move the scripts to `resources/scripts/` or `storage/app/scripts/` (outside the web root), delete `build.zip` and `__pycache__`, and add them to `.gitignore`.

### M-08 Fingerprint-device credentials stored in plaintext and sent to the browser

**Affected:** `app/Livewire/Hr/Attendance/Fpdevices.php:90-104` (loads `password` into a public `deviceForm`), `app/Models/FpDevice.php` (no `encrypted` cast).
**Remediation.** Cast `password` as `encrypted`. Don't hydrate it into public properties. Use a write-only field.

### M-09 Race conditions in one-time tokens and approval workflows

**Affected:** `TwoFactorToken::findValidToken` / `markAsUsed`, `PasswordResetToken` (same pattern), `Leaveapproval::submitDecision`, `Loanapproval::approve`, `Requestloan::save` (check-then-insert for "existing loan").
**Description.** Check-then-act without locking or uniqueness constraints allows double use of a code, duplicate approvals at the same level, and multiple concurrent loan requests that bypass the "one active loan" rule.
**Remediation.** Use atomic conditional updates (`UPDATE ... SET used=1 WHERE id=? AND used=0`, then check affected rows), `DB::transaction()` with `lockForUpdate()`, and DB unique indexes, e.g. `(leave_request_id, approval_level_id)`.

### M-10 Sensitive HR documents publicly accessible without authorization

**Affected:** all `->store(..., 'public')` calls: contracts (`Contracts/ContractDetails.php:97`, `Hr/Staffs/Contracts.php:139`), leave medical documents (`Hr/Leave/Requestleave.php:478,564`, `Hr/Staffs/Leave.php:185`), disciplinary, qualifications and promotions attachments, contract requests (`Hr/Contract/*`), procurement quotations, activity proofs, staff photos.
**Description.** Anyone holding or leaking a URL (browser history, email forwarding, proxy logs, referrers) can fetch these files forever with no login. Filenames are random (40-char hash), which limits guessing, but there is no access control, revocation or audit trail.
**Remediation.** Store on the private disk (ideally via `EncryptedFileStore`) and stream through policy-checked controllers, modelled on `TicketAttachmentController`. Migrate existing files.

## 7. Positive security controls observed

These are well implemented and should be kept and used as templates:

- **Chat module.** `ConversationPane::guard()` re-checks membership on **every** request. Message lookups are scoped to the conversation (`ChatMessage::where('conversation_id', ...)`). Broadcast channels authorize membership (`routes/channels.php`). `#[Locked]` is used for IDs. Sends are rate limited (`ChatService.php:233`). Markdown is rendered with `html_input => strip` and `allow_unsafe_links => false`.
- **Encrypted attachment storage.** `App\Support\EncryptedFileStore` encrypts ticket and chat files with AES-256 on the private disk under random UUID names, with an extension allow-list.
- **Authorizing download controllers.** `TicketAttachmentController`, `ChatController::attachment` and `PerformanceEvidenceController` check access (including private notes) before streaming, set `X-Content-Type-Options: nosniff`, and sanitise `Content-Disposition`.
- **Rich-text sanitisation.** `HtmlSanitizer` uses a DOM-based allow-list, strips `script/style/iframe/object/embed`, restricts `href` schemes and forces `rel="noopener noreferrer"`.
- **Sync-API middleware.** Fails closed when unconfigured and uses `hash_equals` for constant-time comparison. The configured token is 64 characters.
- **Service-layer access helpers** (`TicketAccess`, `EngineeringAccess`, `RosterAccess`, `AssetTransferService`, `EvaluationWorkflow`, `*PlanAccess`) apply permission and scope checks, and the newer modules (Tickets, Engineering, Performance, Assets, Roster) use them consistently. Extend this pattern to HR, Setup, Payroll and ACL.
- **Log viewer** is gated to super-admins via the `viewLogViewer` Gate, with a test (`tests/Feature/LogViewerAccessTest.php`).
- **SQL.** No raw SQL was found built from user input. Raw expressions are static, and `Requestleave` uses a sort allow-list.
- **CSRF.** Livewire enforces CSRF tokens on `/livewire/update`. No state-changing GET controllers were found. API routes are stateless.
- **Passwords** are hashed with bcrypt (12 rounds, `'password' => 'hashed'` cast). `ChangePassword` requires `current_password` and a strong rule. Reset calls `logoutOtherDevices()`.
- **Auditing.** Spatie Activitylog is enabled with `logExcept(['password','remember_token'])`, and role changes are explicitly logged.
- **Session** is regenerated on login, and invalidated with a rotated CSRF token on logout. Cookies are `HttpOnly` with `SameSite=Lax`.
- **Global `QueryException` handler** hides SQL errors from users.
- `.env` is git-ignored and has never been committed (`git log --all -- .env` is empty).
