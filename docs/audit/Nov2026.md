## 1. Executive summary

A lot has improved since the first audit. Backup handling, file uploads, OS command execution, the SMS gateway, password reset, 2FA, User Management/ACL, HR document storage, security headers and dependency versions have all been rebuilt with good controls (see §8 and §9). Composer reports **no known vulnerabilities**.

The application is **still not safe to expose to untrusted users.** Two problems remain:

1. **Most authorization is still missing.** **93 of 161 Livewire components contain no authorization check.** About 20 of these are self-service pages or thin wrappers; the other ~70 are administrative, HR, payroll and approval screens reachable by any logged-in employee. The hardened User Management screen can be bypassed entirely: **`Addstaff` lets any authenticated user create a new login account with any role (including administrator) and a password of their choosing** (C-01).
2. **Livewire state is trusted.** Several components keep authorization decisions or ownership/status fields in public, unlocked properties the browser can rewrite. Any employee can therefore approve leave at any level (H-01), submit leave already marked *Approved* (H-02), request a 0 %-interest loan above the product limit (H-02), and change any contract's base salary (C-03).

Two items from the first audit are **still open and remain critical**: the hard-coded super-admin credential in `UserSeeder` (C-04) and the 10 MB legacy HR database dump tracked in git and pushed to GitHub (C-05).

### Top 5 actions (do these first)

1. **Lock down `Addstaff`, `Stafflist`, `Salary`, payroll and every `Hr/Staffs/*` component today.** Add a `boot()` permission check (as `UserManagement` already does), and route **all** account creation and role assignment through `App\Services\Acl\AccessControl` (C-01, C-02, C-03).
2. **Stop trusting Livewire state.** Mark identity, ownership, status and authorization fields `#[Locked]` or recompute them server-side inside each action. Start with `Leaveapproval::$userApprovalLevels`, `Requestleave::$status/$employee_id`, `Requestloan::$employee_id/$interest_rate/$max_*`, `Salary::$contract_id`, `Addstaff::$user_id` and `Loanapproval::$hasEmployeeAccount` (H-01, H-02, C-03).
3. **Rotate and purge.** Change the seeded super-admin password, remove the hard-coded value from `UserSeeder`, and purge `docs/user-manual/tshrp(1).sql` from git history (`git filter-repo`), then force-push and ask collaborators to re-clone (C-04, C-05).
4. **Enforce segregation of duties** in leave, loan, payment, contract and certificate approvals: the approver must be assigned, must not be the requester, and each decision must be atomic (H-01, H-03, M-08).
5. **Authenticate `/api/attendance/receive`** and add `throttle` to the API group. Make the production `.env` safe: `APP_DEBUG=false`, `APP_ENV=production`, 2FA on, CSP enforced, least-privilege DB user, https `APP_URL`, secure cookies (H-04, H-05).

## 2. Risk rating method

**Severity = Impact × Likelihood**, adjusted for exploit preconditions.

- **Impact:** confidentiality, integrity and availability of HR, payroll and personal data, of financial workflows (salary, loans, payroll), and of the host server.
- **Likelihood:** *High* means any authenticated user (or the internet) can exploit it with a browser and DevTools. *Medium* needs specific knowledge, timing or network position. *Low* needs privileged access or unusual conditions.
- **Livewire threat model.** Every public Livewire method is an HTTP endpoint reachable through `POST /livewire/update`. Every public property without `#[Locked]` is user input: it can be changed with `Livewire.find(id).set(...)`, `$wire.prop = ...`, or by replaying the update request. Route middleware runs only on the initial page load; `boot()` runs on every request. A check that lives only in the view (hidden button) or only in `mount()` does not protect actions.

## 3. Critical findings

### C-01 Privilege escalation: any user can create an administrator account through `Addstaff`

| | |
|---|---|
| **Severity** | 🔴 Critical (CVSS 3.1 ≈ 9.9, AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H) |
| **Category** | OWASP A01 Broken Access Control: privilege escalation, mass assignment |
| **Likelihood** | High: any authenticated user |
| **Status** | **New.** This bypasses the controls that fixed the earlier C-02 |
| **Affected** | `routes/web.php:147-148` (`hr.addstaff`, `hr.editstaff`: `auth` only); `app/Livewire/Hr/Staffs/Addstaff.php:44-52, 109` (unlocked `createUserAccount`, `username`, `user_password`, `selected_role`, `user_id`); `:470` `save()`; `:548-555` (role rule is only `exists:roles,id`); `:603-615` (`User::create` with a client-chosen password); `:673-675`, `:719-721` (`assignRole`); `:640-662` (`user_id` written to the employee record) |

**Description.** `Addstaff` has no authorization in `mount()`, `boot()` or `save()`. When `createUserAccount` is true, `save()` creates a `User` with a client-supplied username and password and assigns **any** role whose ID exists. This skips `AccessControl`'s no-escalation rules, the admin password confirmation and the strong password policy that protect `Users/UserManagement`. Separately, `user_id` is an unlocked public property written straight into `employees.user_id`. An attacker can therefore link their own login to another employee's record, for example a head of department. Supervision, approval mappings (`LeaveApprovalChain::mappingsFor()`), `DepartmentSupervision`, performance access and profile pages all resolve "who am I" through that link. `Stafflist::sendCredentialsToSelected()` (`Stafflist.php:155-250`) is also unprotected and links employees to *existing* accounts by matching e-mail.

**Proof of concept (safe, test instance only).**
1. Log in as a low-privilege employee and open `/hr/staffs/addstaff`.
2. In DevTools: `$wire.createUserAccount = true; $wire.selected_role = '<admin-role-uuid>'; $wire.username = 'x'; $wire.user_password = $wire.user_password_confirmation = 'P@ssw0rd!x'`. Role IDs are rendered in the role `<select>` because `listdata()` loads every role.
3. Fill the mandatory employee fields and submit. Log in as `x`: the account holds the administrator role.
4. Variant: open `/hr/staffs/addstaff/edit/<own-employee-id>`, set `$wire.user_id = '<victim-user-uuid>'`, save, and the victim's login now resolves to your employee record (or the reverse).

**Impact.** Full administrative takeover by any employee, with no password confirmation and no escalation check. Identity confusion across every module that maps users to employees.

**Remediation.**
1. Add `boot(): abort_unless(Auth::user()?->can('manage-staff'), 403)` to `Addstaff`, `Stafflist`, `Importstaffs` and `Staffdetails`, and gate the routes with `->middleware('can:manage-staff')`.
2. Move account creation out of `Addstaff` into a service that calls `AccessControl::canGrantRole()` / `canManageUser()`, requires `ConfirmsAdminPassword`, and applies the strong password rule. Better still, always issue a setup link (`AccountSetupService`) and never accept an admin-typed password.
3. Mark `user_id` `#[Locked]`. Change user↔employee links only through an explicit, permission-checked, audited action.
4. Add a feature test: a role-less user calling `save()` with `createUserAccount=true` gets 403 and creates no `users` row.

**Verification.** As a user without `manage-staff`, loading `/hr/staffs/addstaff` returns 403, and replaying a `save` call returns 403 with no new user or role assignment. A `manage-staff` user who is not a super-admin cannot assign a role whose permissions they do not hold.

### C-03 Payroll and compensation tampering by any employee

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Category** | A01 Broken Access Control; A04 Insecure Design (business logic) |
| **Likelihood** | High |
| **Affected** | `app/Livewire/Hr/Staffs/Salary.php:17-31` (unlocked `$contract_id`, `$salary`, `$employee_id`), `:129-175` `saveSalary()`; `app/Livewire/Acc/Payroll/Payrollgeneration.php:149` `generatePayrollForSelected()`, `:224` public `generatePayroll(Employee $employee, Employeecontracts $contract)`; `Acc/Payroll/Allowancepayment.php:132` `processAllowancePayments()`; `payrolls` table has no unique `(employee_id, period)` index |

**Description.** `saveSalary()` updates `Employeecontracts::find($this->contract_id)->base_salary` and rewrites that contract's allowances and deductions. Nothing checks who is calling, or that `contract_id` belongs to the page's employee. Livewire resolves model-typed arguments of public actions, so `generatePayroll()` can be invoked directly with *any* employee/contract pair; the salary of contract B is then booked as payroll for employee A. Duplicate prevention is a check-then-insert with no unique constraint (see M-08).

**PoC (test instance).** Open `/hr/staffs/salary/<own-employee-id>`, run `$wire.salary = 99999999; $wire.selectedAllowances = [<every allowance id>]; $wire.selectedDeductions = []; $wire.saveSalary()`. Your active contract now carries that salary, and the next payroll run pays it.

**Impact.** Direct financial fraud: inflated salaries, removed deductions (PAYE/pension), fabricated payroll.

**Remediation.** Gate `Salary` with `manage-payroll`/`manage-staff` in `boot()`. Lock `contract_id`/`employee_id` and re-derive the contract server-side (`Employeecontracts::where('employee_id', $this->employee_id)->where('status','active')->firstOrFail()`). Make `generatePayroll()` `protected`. Add a unique index on `payrolls(employee_id, period)`. Require maker-checker approval for salary changes and log old and new values.

**Verification.** A non-payroll user gets 403. A crafted `contract_id` belonging to another employee is rejected. Calling `generatePayroll` from the client fails (method not callable). Inserting a duplicate payroll violates the unique index.

### C-04 Hard-coded super-admin credential in source control

| | |
|---|---|
| **Severity** | 🔴 Critical (if the seeder has ever run on a reachable instance and the password was not changed) |
| **Category** | A07 Identification and Authentication Failures; CWE-798 |
| **Status** | Earlier C-06: **still open** |
| **Affected** | `database/seeders/UserSeeder.php:17-29` (called from `DatabaseSeeder.php:15`) |

**Description.** The seeder creates `username = admin` with `is_super_admin = true`. **Its password is the account's own e-mail address**, which is printed in the same file and echoed to the console. `Gate::before` (`AppServiceProvider.php:38`) grants super-admins every ability. The file is pushed to the GitHub remote.

**Remediation.** Change the live super-admin password now and revoke its sessions and trusted devices. Never commit a usable password. Treat the old value as public even after rewriting history.

**Verification.** `grep -rn "Hash::make('" database/seeders` returns nothing. Logging in with the old password fails on every environment.

## 4. High findings

### H-01 Leave approval authorization is decided by client-controlled state

| | |
|---|---|
| **Severity** | 🟠 High |
| **Category** | A01 Broken Access Control (CWE-639 / CWE-472, external control of an authorization decision) |
| **Affected** | `app/Livewire/Hr/Leave/Leaveapproval.php:32` (`public $userApprovalLevels`, not locked), `:77-84` (filled once in `mount()`), `:118-124` `userCanApproveLevel()`, `:169-231` `submitDecision()`; `app/Services/Leave/LeaveApprovalChain.php:300-314` `mappingsCover()` |

**Description.** `submitDecision()` authorizes the approver by checking `$this->userApprovalLevels`. That is a public array the browser can overwrite, and it is never recomputed on later requests. Setting `[{approval_level_id: <level>, department_ids: []}]` covers that level for **every** department. `openApproveModal($leaveId)` loads any leave by ID, and nothing stops an employee approving their own request.

**PoC.** Any user opens `/hr/leave/leaveapproval` and runs `$wire.openApproveModal('<leave-id>')` and `$wire.$set('userApprovalLevels', [{approval_level_id:'<level-1-id>', department_ids:[]}])`, sets a comment, then calls `$wire.submitDecision()`. Repeat for each level until the leave is fully approved.

**Impact.** Any employee can approve or reject any leave, including their own, at every level. This is fraud against paid leave and staffing.

**Remediation.** Make `userApprovalLevels` a computed value (`#[Computed]`), or call `$this->chain()->mappingsFor(Auth::user())` inside `submitDecision()`. Store only the selected leave's ID, `#[Locked]`, and re-load it. Reject decisions where `$leave->employee->user_id === Auth::id()`. Wrap the decision in a transaction with `lockForUpdate()` and re-check `nextLevel()` inside it.

**Verification.** Tampering with `userApprovalLevels` has no effect. A self-approval attempt is refused. Two concurrent approvals at the same level produce one decision row.

### H-02 Mass assignment in self-service leave and loan requests

| | |
|---|---|
| **Severity** | 🟠 High |
| **Category** | A01 / A04: mass assignment, business-logic bypass |
| **Status** | Earlier H-05: **still open** |
| **Affected** | `app/Livewire/Hr/Leave/Requestleave.php:82` (`$employee_id`), `:88` (`$status = 'Awaiting'`), `:92` (`$hasEmployeeRecord`), `:451-500` `save()` writes `'status' => $this->status, 'employee_id' => $this->employee_id`; `leave_id` is validated only as `required`. `app/Livewire/Hr/Loan/Requestloan.php:25-64` (`$employee_id`, `$interest_rate`, `$interest_type`, `$min_amount`, `$max_amount`, `$max_period`, `$installment_amount`, `$hasEmployeeAccount`, none locked), `:73-83` rules use the client-held `min/max`, `:290-320` `save()` |

**Description.**
- **Leave:** a request can be created with `status = 'Approved'`, skipping the approval chain, and filed in another employee's name (`employee_id`). The leave-type ID is not checked with `exists:`.
- **Loan:** `interest_rate` is copied from the client into `loanrequests`, so 0 % is possible. The amount and period limits are validated against `max_amount`/`max_period`, which the client controls. `employee_id` can name someone else, and `installment_amount` is stored as sent.

**PoC.** On `/hr/leave/leaverequest`: `$wire.status = 'Approved'`, fill the form, `$wire.save()`. On `/hr/loan/requestloan`: `$wire.interest_rate = 0; $wire.max_amount = 1e9; $wire.amount = 50000000`, then `$wire.save()`.

**Remediation.** Never read `status`, `employee_id`, rates or limits from component state when saving. Re-derive the employee from `Auth::id()`, hard-code the initial status, and reload the `loan_items` row in `save()` to take rate, limits and period from it. Recompute the installment server-side. Add `exists:leaves,id` (active only). Mark display-only properties `#[Locked]`.

**Verification.** Tampered values are ignored. A stored leave always starts in the initial status, and a stored loan always carries the product's interest rate.

### H-03 Approval and finance workflows lack assignment checks and segregation of duties

| | |
|---|---|
| **Severity** | 🟠 High |
| **Category** | A01 / A04 |
| **Status** | Earlier H-06: **still open** |
| **Affected** | `Hr/Loan/Loanapproval.php:23` (`$hasEmployeeAccount` unlocked), `:164-175` open modals for any ID, `:206` `approve()`, `:267` `reject()`, `:311` `markUnderReview($id)`; `Hr/Loan/Loanpayments.php:171-200` `recordPayment()`; `Contracts/ContractDetails.php:181-203` `approveContract($approvalId)` (and `rejectContract`); `Hr/Contract/CertificateOfServiceManagement.php:334` `approveCertificate($id)`, `:387` `markAsPrinted($id)`; `Hr/Contract/ContractRequestManagement.php:98` `approveRequest()`, `:171` `rejectRequest()` |

**Description.**
- Any user linked to an employee record can approve or reject **any** loan, including their own, and record repayments against any loan (marking it paid).
- `approveContract($approvalId)` approves any `contract_approvals` row, even one not belonging to the contract on screen and not assigned to the caller. When the last row is approved, the contract becomes `active`.
- Certificates of service and contract-change requests can be approved by anyone who can reach the page, which is everyone.

**Remediation.** For each workflow, check that (a) the caller holds the workflow permission, (b) the caller is the assigned approver for that step (`approver_id`/mapping), (c) the caller is not the requester or beneficiary, and (d) the record belongs to the parent shown (`$this->contract->approvals()->findOrFail($approvalId)`). Make decisions atomic (see M-08). Audit-log every decision with the actor.

**Verification.** Negative tests for each rule: unassigned approver, self-approval, foreign record, double submission.

### H-04 Unauthenticated attendance injection endpoint

| | |
|---|---|
| **Severity** | 🟠 High |
| **Category** | A01 / A07: missing authentication; A04 |
| **Status** | Earlier H-03: **still open** |
| **Affected** | `routes/api.php:18` `POST /api/attendance/receive` (outside the `api.token` group, no `throttle`); `app/Http/Controllers/Api/AttendanceLogController.php:33-108` |

**Description.** Anyone on the internet can post an unbounded JSON array of `{user_id, timestamp}`. Records are inserted into `employeeattendances` with no device authentication, no check that `user_id` is a known fingerprint user, no batch size limit, and timestamps the client chooses (any date). Every failure is logged with the full record, so the endpoint also floods the logs.

**Impact.** Forged or erased presence records used for HR decisions, disciplinary cases and performance views. Database and log flooding (DoS).

**Remediation.** Move the route into the `api.token` group, or give devices their own HMAC or per-device token (the external attendance bridge already authenticates with `ATTENDANCE_BRIDGE_TOKEN`). Add `throttle:60,1`. Cap the batch size (e.g. 1,000). Validate `user_id` against `fpusers` and timestamps against a sane window. Add a unique index on `(fpuser_id, clocktimestamp)` instead of check-then-insert. If the legacy endpoint is no longer used, remove it.

**Verification.** An unauthenticated POST returns 401. A batch over the limit returns 422. A replay creates no duplicates.

### H-05 Production-unsafe environment configuration

| | |
|---|---|
| **Severity** | 🟠 High (Critical if this `.env` is used on a reachable host) |
| **Category** | A05 Security Misconfiguration |
| **Status** | Earlier H-09: **still open** |
| **Affected** | `.env` (working copy) |

| Setting | Current | Risk | Production value |
|---|---|---|---|
| `APP_ENV` / `APP_DEBUG` | `local` / `true` | Ignition-style stack traces, env and query disclosure on any error | `production` / `false` |
| `DB_USERNAME` / password (also `TSHRP_DB_*`) | `root`, short dictionary-style password | Full DB server compromise from any SQL or credential leak | Dedicated least-privilege user, long random password |
| `TWO_FACTOR_ENABLED` | `false` | 2FA disabled for everyone; password alone grants access | `true` |
| `CSP_REPORT_ONLY` | `true` | CSP blocks nothing; XSS defence-in-depth is off. This is also why 3 `SecurityHeadersTest` cases fail | `false` |
| `APP_URL` | `http://localhost` | Account setup links are built from `APP_URL` (`AccountSetupService::url()`), so they would be wrong and use plain http | Public `https://` URL |
| `SESSION_SECURE_COOKIE` | unset | Session cookie can travel over http | `true` |
| `SESSION_ENCRYPT` | `false` | Session payloads (2FA/reset state) stored in clear in the DB | `true` (optional hardening) |
| `LOG_LEVEL` | `debug` | Verbose logs, larger exposure if logs leak | `warning` or `info` |
| File mode of `.env` | `0664` (world-readable) | Any local user can read every secret | `0640`, owned by the deploy user, group web server |
| Mail password, Reverb secret, `EXPORT_API_TOKEN`, `BACKUP_ARCHIVE_PASSWORD` | Present | Fine in `.env`, but rotate any value that has been shared or copied around | Store in a secret manager; rotate |

`.env` has never been committed (`git log --all -- .env` is empty), which is good.

**Verification.** A forced error on production shows a generic 500 page. The response carries an enforcing `Content-Security-Policy` header. Login triggers 2FA. `stat -c %a .env` prints `640`.

## 5. Medium findings

### M-01 Trusted-device "fingerprint" is predictable (2FA bypass with a stolen password)

- **Affected:** `app/Services/DeviceFingerprinter.php:13-25`, `app/Livewire/Auth/Login.php:68-87`, `app/Models/TrustedDevice.php:96-106`. **Earlier H-02, still open** (downgraded: 2FA is currently disabled anyway, see H-05).
- **Issue:** The fingerprint is `sha256(User-Agent | /24 network | Accept-Language | Accept-Encoding)`. All four values are sent by the client and guessable, and colleagues behind the same office NAT share the /24. An attacker who has a victim's password and copies their browser headers skips 2FA for up to 30 days.
- **Fix:** On successful 2FA, issue a random 256-bit device token in an `HttpOnly; Secure; SameSite=Strict` cookie. Store only its hash in `trusted_devices` and require it, with the fingerprint as a secondary signal only. Revoke tokens on password change (already done for reset and setup; also do it in `ChangePassword`, see M-06).
- **Verify:** Replaying the headers without the device cookie triggers 2FA.

### M-02 Session lifetime, "remember device" and session revocation

- **Affected:** `app/Livewire/Auth/TwoFactorsAuthentication.php:107` `Auth::login($user, $this->remember_device)`; `app/Livewire/Users/ChangePassword.php:73-84` (`logoutOtherDevices` commented out); `config/session.php`.
- **Issue:** (a) Ticking "trust this device" also issues a Laravel *remember-me* cookie, valid for about 400 days by default, so the 30-day device trust becomes a year-long login. (b) Changing your password does not end other sessions, rotate `remember_token`, or revoke trusted devices. A user who changes their password after suspecting compromise stays compromised. (c) There is no idle or absolute timeout for privileged sessions beyond `SESSION_LIFETIME=120`.
- **Fix:** Pass `false` for `remember` (device trust and remember-me are separate concepts), or cap the remember cookie lifetime. In `ChangePassword`, call `Auth::logoutOtherDevices()`, rotate `remember_token`, and deactivate `TrustedDevice` rows. Consider shorter lifetimes for admin roles.
- **Verify:** After a password change, another browser's session is logged out. No `remember_web_*` cookie is set at 2FA.

### M-03 Sync API: single all-powerful static token, no rate limiting, full PII returned

- **Affected:** `routes/api.php:21-58`, `app/Http/Middleware/VerifyApiToken.php:56-76`, `app/Http/Controllers/Api/*Controller.php` (`index`/`show`), `app/Models/Employee.php` (no `$hidden`). **Earlier M-04, partially fixed** (fails closed, constant-time comparison).
- **Issue:** One shared token reads and writes employees, leaves, contracts, assets and attendance. It is also accepted in the request **body** (`token=`), where it ends up in proxy/WAF logs. The `api` group has no `throttle` middleware. Employee responses serialise every column, including `national_id` and `tin_number`, plus related records. 11 API error responses return `'error' => $e->getMessage()`. With no `config/cors.php`, Laravel's default CORS allows any origin on `api/*`.
- **Fix:** Use per-client tokens (Sanctum personal access tokens with abilities such as `employees:read` and `attendance:write`) or HMAC-signed requests. Accept the header form only. Add `->middleware('throttle:api')` and define the limiter. Return API Resources with an explicit field allow-list. Replace `getMessage()` with a correlation ID. Publish `config/cors.php` with no browser origins, or only explicit ones.
- **Verify:** A read-only token cannot `POST`. More than N requests per minute return 429. Responses contain no `national_id` unless required.

### M-04 IDOR reads in self-service and approver components

- **Affected:** `Hr/Loan/Loanbalance.php:120-127` `openDetailsModal($id)` (any loan, with payment history); `Hr/Leave/Leaveapproval.php:131-158` `openApproveModal`/`viewApprovalHistory` (any leave with employee details); `Hr/Leave/Leavebalance.php` (unlocked `$employee_id`, used at `:52`); `Hr/Loan/Loanapproval.php:164-175`; `Acc/Payroll/Payrollgeneration.php:121` `viewContractDetails($contractId)`.
- **Issue:** Records are fetched by a client-supplied ID with no ownership or scope filter.
- **Fix:** Scope every lookup (`loanrequests::where('employee_id', $this->currentEmployee->id)->findOrFail($id)`; leave queries through `LeaveApprovalChain::pendingFor()` or an ownership check). Lock derived identity properties.
- **Verify:** Supplying another employee's record ID returns 404.

### M-05 Exception details disclosed to end users

- **Affected:** About 73 Livewire call sites flash or toast `$e->getMessage()` (for example `Hr/Staffs/Salary.php:172`, `Acc/Payroll/Payrollgeneration.php:192,213`, `Hr/Attendance/Fpdevices.php:293-294`, `Hr/Roster/Editroster.php:194`, `Hr/Staffs/Addstaff.php:628`), plus 11 in API controllers. **Earlier M-05, still open.** Intentional domain exceptions (`TicketActionException`, `ChatActionException`, `AssetActionException`, `EngineeringActionException`) are fine.
- **Issue:** Raw exception text leaks SQL fragments, table and column names, file paths and upstream service errors. The global `QueryException` handler only applies when the exception escapes the component.
- **Fix:** Catch only domain exceptions for user messages. For everything else, log with context and show a generic message with a reference ID.
- **Verify:** `grep -rn "getMessage()" app/Livewire app/Http` hits only domain-exception handlers.

### M-06 Inconsistent password policy

- **Affected:** `Auth/ResetPassword.php:30,123`, `Auth/SetupAccount.php:40` and `Hr/Staffs/Addstaff.php:551` use `min:8` only; `Users/ChangePassword.php:24-30` requires letters, mixed case, numbers and symbols; `UserManagement` uses the strong rule. **Earlier M-06, partially fixed.**
- **Fix:** Define `Password::defaults()` once in `AppServiceProvider` (min 12, mixed case, numbers, `uncompromised()`), and use `Password::defaults()` everywhere.
- **Verify:** `Password1` is rejected on reset, setup and admin creation.

### M-07 No trusted-proxy configuration

- **Affected:** `bootstrap/app.php` (no `trustProxies()`); every consumer of `request()->ip()` and `isSecure()`: `AuthThrottle` keys, `DeviceFingerprinter`, `SecurityHeaders` HSTS and `upgrade-insecure-requests`, activity logging.
- **Issue:** Behind a reverse proxy or load balancer, every request appears to come from the proxy IP and over http. Per-IP login, 2FA and reset limits then become one global bucket: one attacker can lock everyone out, while per-IP brute-force protection disappears. HSTS is never sent because `isSecure()` is false.
- **Fix:** `$middleware->trustProxies(at: ['10.0.0.0/8', ...], headers: Request::HEADER_X_FORWARDED_FOR | ... )` listing only your proxy addresses. Never use `*` on a directly exposed host.
- **Verify:** Through the proxy, `request()->ip()` shows the client IP, and HTTPS responses carry `Strict-Transport-Security`.

### M-08 Race conditions in approval and payroll workflows

- **Affected:** `Leaveapproval::submitDecision()`, `Loanapproval::approve()`, `Loanpayments::recordPayment()` (transaction but no row lock), `Payrollgeneration::generatePayrollForSelected()` (check-then-insert, no unique index), `Requestloan::save()` (`checkExistingLoan()` then insert). **Earlier M-09, partially fixed**: OTP, reset and setup tokens now use atomic consumption.
- **Issue:** Concurrent requests can record two decisions for one level, approve a loan twice, overpay, or create duplicate payroll rows.
- **Fix:** Use `DB::transaction` with `lockForUpdate()` on the parent record, re-validate the state inside the lock, and add unique indexes (`leaverequestapprovals(leave_request_id, approval_level_id)`, `payrolls(employee_id, period)`).
- **Verify:** A parallel-request test (e.g. 20 concurrent calls) produces exactly one effect.

## 8. Positive security controls observed

Keep these, and use them as templates when fixing the findings above:

- **Livewire authorization pattern done right.** `UserManagement`, `Acl/*`, `Fpdevices`, `Smsapis`, `Smslogs`, `Engineering/Setup`, `ChatAnalytics`, `TicketDashboard`, `TicketCategories`, `PerformanceDashboard` and the roster components check in `boot()` (every request), and the matching routes carry `can:` middleware.
- **No-escalation ACL service.** `App\Services\Acl\AccessControl` stops non-super-admins granting roles or permissions they do not hold, editing their own role, or managing super-admins. Sensitive changes require a fresh password confirmation (`ConfirmsAdminPassword`, rate limited, allow-listed resumable actions). Sessions are ended when an account is disabled or its password reset.
- **Authentication flows.** Login, 2FA, password reset and account setup are session-bound (no identity in URLs or unlocked props), rate limited per account and per IP, and use constant-time comparison and atomic one-time consumption. Login equalises timing for unknown accounts. Reset revokes trusted devices, sessions and remember tokens and never auto-logs-in. Setup links store only a SHA-256 hash, are single-use, expire, are built from `APP_URL` (not the Host header), and are moved out of the URL with `Referrer-Policy: no-referrer`.
- **Backups.** Server-generated names, an allow-list regex, `realpath` containment and symlink refusal. AES-256 archive encryption, `0600` files in a `0700` directory (verified on disk), zip-slip and size checks. Signed, user-bound, 60-second download URLs with re-authorization. Restore is CLI-only, preceded by a safety backup. DB credentials go through an option file, never argv.
- **File handling.** `HrDocumentStore` and `EncryptedFileStore`: extension, content-sniffed extension and MIME must all agree; files are encrypted at rest on the private disk with random names and served by authorizing controllers (`HrDocumentController`, `TicketAttachmentController`, `ChatController::attachment`, `PerformanceEvidenceController`) with `nosniff`, `no-store` and a sandbox CSP for images. The Livewire global temporary-upload rule refuses scripts, HTML and SVG, and SVG previews are disabled.
- **Outbound requests.** `OutboundUrlGuard` enforces https, port 443 only, a host allow-list, rejection of IP literals and private ranges, and DNS pinning against rebinding. `SecretRedactor` and `RedactSecrets` keep provider credentials out of logs. SMS API keys use the `encrypted` cast and are `$hidden`.
- **Command execution.** Only array-form `Process::run([...])` with validated arguments. No `exec`, `shell_exec`, `system`, `eval` or `unserialize` on user data.
- **SQL.** No raw SQL built from user input. Raw expressions are static, and `Requestleave` uses a sort allow-list.
- **XSS.** Blade escaping throughout. The only `{!! !!}` sinks are DOM allow-list sanitised (`HtmlSanitizer`, which now also blocks protocol-relative and backslash hrefs), `nl2br(e(...))`, the chat `MessageRenderer`, or static framework output. `SecurityHeaders` sets a nonce-based CSP (no `'unsafe-inline'` scripts), `frame-ancestors 'none'`, `nosniff`, COOP, `Permissions-Policy` and HSTS on HTTPS, with a throttled CSP report endpoint that logs only paths.
- **CSRF.** Livewire enforces tokens. The only exemption is `csp-report`. No state-changing GET routes (logout is a Livewire action).
- **Sync API middleware** fails closed when no token is configured and compares in constant time.
- **Log viewer** is gated to super-admins (`viewLogViewer`), with a tracked test.
- **Auditing.** Spatie Activitylog with `logExcept(['password','remember_token'])`; user, role, backup and HR-document access events are explicitly logged.
- **Secrets hygiene.** `.env` was never committed; `.env.example` has empty secrets; FP-device passwords are write-only in the UI.
